## Overview

The finale has two sub-phases:
1. **Vote** — audience answers emotional questions on their phones; answers generate tokens in a shared pool
2. **Remix** — the performer arranges tokens on a pentagon of 5 granular types, building the finale song in real time

## Core Concept: The Token Pool

The finale song is built from a **pool of tokens**. Each token is tied to a chapter (Ambition, Love, or Avoidance) and was generated by an audience member's answer to an emotional question. The performer places tokens onto a **pentagon of 5 granular type nodes** (bass, drums, pad, harmony, fx). Each node can hold one active token at a time — the token's chapter determines which song's material plays for that granular type.

The result is a live, evolving composition: the performer curates which chapter's material fills each instrument role, crossfading between songs as they swap tokens in and out. When `audienceInteraction` is enabled, audience members can also queue tokens, creating a shared remix experience.

## Narrative Setup

After Song 3's resolution, the performer "abandons" the stage. NPC message: *"He's gone. We need to do this ourselves."* The audience generates the raw material (tokens) through emotional reflection, then the performer returns to shape it into a final song.

## Phase 1: Vote (`finale_vote`)

Audience members answer emotional questions on their phones. Each answer maps to a chapter and generates a token in the shared pool.

### Question Flow

1. Each audience member sees one question at a time on their phone (e.g., "What does he need to hear?")
2. Questions are served from a question bank defined in `VotePhaseConfig.questions`
3. Each answer maps to a chapter (ambition / love / avoidance) and generates a token in the pool
4. After answering, the next question is delivered via the `next_question` event
5. Each person can answer up to `maxQuestionsPerPerson` questions, derived from `targetPoolSize / audienceCount`
6. When the pool reaches `targetPoolSize`, `poolCapReached` becomes `true` and phones go dark (`vote_complete` event)

### Token Structure

Each token records its origin:

```typescript
interface Token {
  id: string;                    // Unique token ID
  chapter: Chapter;              // 'ambition' | 'love' | 'avoidance'
  questionIndex: number;         // Which question generated this token
  userId: UserId;                // Who answered
}
```

### Pool State

The pool tracks token counts by chapter so the projector can visualize the distribution:

```typescript
pool: {
  tokens: Token[];
  availableByChapter: Map<string, number>;   // Tokens not currently active/queued, by chapter
  totalByChapter: Map<string, number>;       // All tokens generated, by chapter
  totalRemaining: number;                     // Tokens available for placement
  targetPoolSize: number;                     // Pool cap
}
```

## Phase 2: Remix (`finale_remix`)

The performer arranges tokens from the pool onto a pentagon of 5 granular type nodes. The audience hears the composition evolve in real time.

### Pentagon Structure

5 granular type nodes arranged as a pentagon:
- **Bass**
- **Drums**
- **Pad**
- **Harmony**
- **FX**

Each node can hold one **active token** at a time. The active token's chapter determines which song's material plays for that granular type:

```
trackIndices = trackMap[granularType][songIndex]
```

Where `songIndex` is derived from the token's chapter (ambition=0, love=1, avoidance=2).

### Token Queuing and Activation

Token placement is **loop-quantized**:

1. The performer (or audience, when `audienceInteraction` is enabled) **queues** a token on a node
2. Queued tokens wait until the next loop boundary
3. At the loop boundary, the queued token becomes **active**, replacing any previously active token on that node
4. The outgoing track crossfades out and the incoming track crossfades in (beat-locked via the timing engine)

### Audience Interaction

When `audienceInteraction` is enabled (`TOGGLE_AUDIENCE_INTERACTION` command):
- Audience members can also queue tokens onto nodes
- Audience-queued tokens take effect with instant crossfade (no loop-boundary wait)
- Tokens loop persistently once active

### Audio Behavior

- **Track resolution:** Each active token resolves to Ableton tracks via `trackMap[granularType][songIndex] -> trackIndices`. The track map is config-driven (defined in `default-show.json`).
- **Crossfades:** All performer-initiated token swaps crossfade at loop boundaries (beat-locked). Audience-initiated swaps (when enabled) crossfade instantly.
- **Empty nodes:** If a node has no active token, that granular type is silent. Silence is musically valid.
- **Loop-quantized timing:** The timing engine (Ableton as source of truth) drives loop boundaries via OSC beat events.

### Performer Controls

The performer's controller interface shows:
- The token pool, filterable by chapter
- The pentagon with current active/queued tokens per node
- Controls for each node:
  - **Queue token:** Select a token from the pool and place it on a node
  - **Dequeue token:** Remove a queued (not yet active) token
  - **Clear node:** Remove the active token, silencing that granular type
- **Toggle audience interaction:** Enable/disable audience token placement
- **End show:** Transition to `ended` phase

## Finale State

```typescript
interface FinaleState {
  phase: 'vote' | 'remix';

  // Vote phase tracking
  vote: {
    questionsAnsweredByUser: Map<UserId, number>;   // Per-user answer count
    maxQuestionsPerPerson: number;                   // Derived: targetPoolSize / audienceCount
    poolCapReached: boolean;                         // True when pool hits target size
  };

  // Token pool
  pool: {
    tokens: Token[];                                 // All generated tokens
    availableByChapter: Map<string, number>;         // Available (not active/queued) tokens per chapter
    totalByChapter: Map<string, number>;             // Total tokens generated per chapter
    totalRemaining: number;                          // Available token count
    targetPoolSize: number;                          // Pool capacity
  };

  // Remix state
  queue: Map<string, QueuedToken[]>;                 // granularType -> queued tokens (waiting for loop boundary)
  active: Map<string, ActiveNode>;                   // granularType -> currently active node state
  audienceInteraction: boolean;                      // Whether audience can queue tokens
  trackMap: Map<string, Map<number, number[]>>;      // granularType -> songIndex -> Ableton trackIndices

  // Playback tracking
  loopCount: number;
  loopProgress: number;                              // 0-1 progress through current loop

  // NPC
  npc: { currentMessage: string | null };
}
```

## Resolved Decisions

- **Token model replaces cell model.** Tokens hold a chapter (mapping to song index), not a grid position. Granular type is determined by which node the token is placed on, not a row index.
- **5 granular types (not 6).** The pentagon has 5 nodes: bass, drums, pad, harmony, fx. Melody/seed is not a separate node.
- **Loop-quantized activation.** Performer token swaps activate at loop boundaries for musical coherence. Audience swaps (when enabled) are instant.
- **One active token per node.** Each granular type can only play one song's material at a time. Queueing a new token replaces the current one at the next loop boundary.
- **Audience interaction is toggled, not always-on.** The performer controls when the audience can participate in remix via `TOGGLE_AUDIENCE_INTERACTION`.
- **Pool cap ends voting.** When `targetPoolSize` is reached, all phones go dark simultaneously. No timer-based ending.
- **Track resolution is config-driven.** `trackMap[granularType][songIndex] -> trackIndices` -- no formula, all defined in `default-show.json`.
